# Планирование и декомпозиция

## Overview

Преобразуй принятую постановку в небольшие результаты, которые можно реализовать и проверить отдельно.
План должен пережить смену исполнителя и показать, почему порядок работ безопасен.
Это адресуемый дополнительный метод; действующий маршрут стадий Brain сохраняется.

## When to Use

1. Требования понятны, но начать мешают размер задачи или неизвестный порядок зависимостей.
2. Нужно выделить сквозные части, оценить риск и определить возможные границы независимой работы.
3. Требуется уточнить существующий план той же задачи.

Не применяй для одного очевидного изменения или уже достаточного плана.
Если неизвестны роли, сценарии и исключения, сначала доведи постановку.
Для 1С этот метод дополняет `architect` и не отменяет входы и проверки стадии.

## Process

### 1. Прочитай постановку без изменения реализации

Запусти из корня Brain `python3 rules/scripts/start_task.py <номер>`.
Прочитай README задачи, её `plan.md` и документы из «Читать сейчас».
Проверь выбранный вариант, ограничения, существующие паттерны, тестовые границы и неизвестное.
Планирование допускает запись плана; реализацию кода на этом шаге не начинай.

Перед изменением существующего плана прочитай его свежую версию.
Сохрани завершённые пункты, доказательства и незавершённую работу других исполнителей.
Для той же задачи обновляй существующий план.
Если обнаружил план другой работы, выясни принадлежность; не очищай чужую очередь.
Уже принятое владельцем решение и действующее разрешение не требуют повторного согласования.

### 2. Построй граф зависимостей

Зависимость означает, что следующий блок нельзя закончить без результата предыдущего.
Отдельно назови внешние предпосылки: доступ, решение, контракт или тестовую базу.

```text
Контракт данных
    ├── Проверка входа ───────┐
    └── Хранение ── API ── UI ── Сквозная проверка сценария
```

Сначала выполни минимальный фундамент для первого сценария.
Не строй все слои целиком до первой проверки пользователя.
Рискованные неизвестные вынеси в ранний проверяемый блок, чтобы дешево опровергнуть подход.

### 3. Разрежь работу по результатам

Горизонтальный план «вся БД → всё API → весь интерфейс → соединить» откладывает обнаружение ошибок.
Сквозные части дают рабочий путь на каждом шаге:

```text
1. Пользователь создаёт запись: хранение + обработчик + форма + проверка.
2. Пользователь видит список: запрос + обработчик + форма + проверка.
3. Пользователь меняет запись: валидация + запись + форма + проверка.
```

Для текстовых скилов сквозная часть — «канон → индекс → адресная доставка → проверка потребителя».
Не копируй веб-слои туда, где нет веб-продукта.

### 4. Запиши блоки в единственном plan.md

Используй `plan.md` в каталоге полной задачи Brain.
Он содержит этапы, атомарные пункты, зависимости, проверки, риски и контрольные точки.
Не создавай отдельные `tasks/plan.md`, `tasks/todo.md`, `tasks.md` или автоматически новые issues.
Принятые решения и основания остаются в README «Решения»; план ссылается на них.

```markdown
## Блок Б2: Пользователь видит сохранённые записи

Результат: список показывает только доступные пользователю записи.
Зависит от: Б1 — контракт доступа и сохранение записи.
Предполагаемые файлы: конкретные пути после чтения репозитория.

Критерии приёмки:
1. Владелец видит свою запись после повторного открытия.
2. Другой пользователь не видит чужую запись.
3. Пустой список имеет понятное состояние.

Проверка: фактическая команда проекта и конкретный ручной сценарий.
Риск: фильтр владельца применяется после пагинации.
Доказательство завершения: результат проверки и ссылка на изменённые файлы.
```

Критерий приёмки отвечает «получили нужное поведение?».
Проверка отвечает «каким действием и свидетельством это подтвердим?».
Общий критерий качества проекта действует дополнительно; не подменяй его новым универсальным барьером.
Для различия этих уровней при необходимости прочитай [Definition of Done](../../references/definition-of-done.md).
Его примеры адаптируй к проверкам проекта, а не превращай в новые обязательства для каждого текстового изменения.

### 5. Проверь размер и порядок

Цель блока — один самостоятельный результат за один сосредоточенный рабочий проход.
Количество файлов — сигнал сложности, а не критерий готовности.

| Сигнал | Решение |
|---|---|
| Одна функция или настройка | Обычно один малый блок |
| Один пользовательский путь через несколько слоёв | Обычно одна средняя сквозная часть |
| Два независимых результата в названии через «и» | Рассмотри разделение |
| Нельзя дать до трёх ясных критериев результата | Проверь границы блока |
| Блок требует более одного сфокусированного прохода или примерно двух часов | Найди промежуточный проверяемый результат |
| Меняется много файлов механически | Оцени доказательство корректности, а не дроби по счётчику файлов |

После двух-трёх блоков обычно полезна контрольная точка: проверки, рабочий сквозной путь, обновлённые риски.
Ставь её по реальной границе риска; не добавляй обязательный вопрос владельцу после каждого блока.
Каждый блок должен оставлять систему в известном рабочем состоянии либо явно описывать временное ограничение.

### 6. Отметь независимость без автоматического делегирования

Независимые части интерфейса, готовые тестовые сценарии и документация могут выполняться параллельно при авторизации.
Изменения схемы, общего состояния и последовательные зависимости требуют порядка.
Общий API сначала получает согласованный контракт.
Этот скил только указывает возможность параллельной работы и не запускает агентов.

Если нужен сосед `mp-to-tickets`, прочитай его канонический `SKILL.md` по пути из `start_task.py` или индекса Brain.
Оба скила обновляют один `plan.md`; второй список задач не появляется.
До исполнения проверь, что план принят в пределах действующей авторизации.
Запрашивай решение только по действительно новой развилке, которая меняет согласованный результат.

## Common Rationalizations

| Оправдание | Что проверить |
|---|---|
| «Разберусь по ходу» | Без графа скрытые зависимости превращают реализацию в переделку |
| «Очевидные задачи можно не записывать» | Следующий исполнитель не знает неявных критериев |
| «Всё помещается в голове» | План должен пережить смену контекста |
| «Старый план устарел, заменю целиком» | Незавершённые пункты могут отражать текущую работу |

## Red Flags

1. Каждый пункт называется «реализовать функциональность» и не имеет проверки.
2. В плане только крупные слои или только перечень файлов.
3. Блокирующие зависимости перепутаны с удобным порядком.
4. Появился второй план или внешний трекер без запроса.
5. Готовность определена числом файлов вместо результата.

## Verification

1. Каждый блок имеет результат, критерии приёмки и применимую проверку с доказательством.
2. Зависимости образуют выполнимый порядок; риски проверяются до дорогих зависимых работ.
3. Первый сквозной сценарий проверяется до завершения всех слоёв.
4. Контрольные точки и границы возврата соответствуют риску.
5. Всё записано в одном `plan.md`; завершённые пункты и разрешения сохранены.
6. Неразрешённые вопросы отделены от исполнимых блоков, а принятый объём не требует повторного разрешения.
